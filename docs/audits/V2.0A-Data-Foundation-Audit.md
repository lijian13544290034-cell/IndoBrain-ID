# V2.0A Content & Membership Data Foundation Audit

## Current data and behaviour

- Experience sources are split across `lib/driver-experiences.ts`, `lib/nanny-experiences.ts`, `lib/factory-experiences.ts`, `lib/module-experiences.ts`, `lib/social-experiences.ts`, `lib/life-experiences.ts`, and `lib/life-business-dating-experiences.ts`.
- Current IDs remain stable (`EXP-DRV`, `EXP-NAN`, `EXP-FAC`, role IDs such as `EXP-PRO`/`EXP-WHS`, `EXP-SOC`, and `EXP-LIF`). No ID migration is proposed.
- All sources share core task/dialogue/harvest fields, but they vary in optional `content`, `explanation`, `category`, and `pattern` fields. `lib/v2/content-foundation.ts` provides a read-only compatibility adapter instead of altering them.
- Harvest achievement normalization is already centralised in `lib/learning-achievements.ts`; V2 reuses it exactly.
- The current Pattern page contains three client-side templates with non-stable IDs. V2 defines stable-ID capability without changing that UI.
- Favorites and completed Experience IDs are stored in the client-side `indobrain_learning_profile_v1` profile. Copying is browser-native. Completion drives local achievement statistics through `getLearningAchievementStats`.
- Server persistence is currently optional, anonymous-session event/progress/feedback storage. `docs/supabase-schema.sql` has no account, membership, role, expiry, or learning-direction table.

## Permission and account audit

There is no current membership authorization layer in this Production baseline. The only server event endpoints are `app/api/events/route.ts`, `app/api/feedback/route.ts`, and the optional Supabase helper `lib/supabase-server.ts`. No role, expiry, membership tier, or `learningDirection` check exists in the inspected routes.

This means V2.0A must not pretend that client storage enforces membership. `lib/v2/membership.ts` therefore supplies types and pure rules only; enforcement belongs in a future server-authenticated release.

## Compatibility guarantees

V2.0A does not modify lesson content, routes, Azure TTS, the existing favorite interaction, completion statistic inputs, login, learning direction, or Production configuration. No database migration or user-data update is executed.

## Inventory and Level calibration

- Visible catalog Experience records: 516. The source-level inventory contains 520 records; four Nanny records currently have no Harvest and are excluded by the existing visible-catalog filter. This release does not alter either set.
- Unique Harvest normalized with the existing achievement rule: 741.
- Current compatible Pattern examples: 3.
- Theoretical maximum Indonesia Power for all visible content: `516 × 5 + 741 × 2 + 3 × 3 = 4071`.

Under the approved temporary thresholds, 4071 reaches L9 (商务达人) but not L10 (印尼通, starting at 5001). That is a sensible signal that L10 should remain an expansion milestone, but the gap is substantial: the next content cycle must either add verified unique content or the product owner should approve a later calibration. V2.0A intentionally does not change any threshold.

The existing content audit also reports seven duplicate Chinese-title groups, nine duplicate Indonesian-line groups, seven duplicate complete-Harvest groups, and four Nanny records without Harvest. These are content-QA follow-ups, not data-foundation changes, so they remain untouched.

## Legacy VIP upgrade procedure (proposal)

1. Obtain an approved six-account roster from the product owner.
2. In non-production, match by immutable account ID (never display name or phone only).
3. Preview a dry-run containing only the six IDs and the planned values: `VIP`, `LEGACY_UPGRADE`, the approved note, and audit actor/time.
4. Obtain a second approval of the dry-run output.
5. Apply an idempotent update only where the account ID is on that roster; retain all other account fields and history.
6. Export an audit result and reconcile exactly six changed rows before any Production approval.

## Enterprise attribution proposal

An organization has one `OWNER` membership and zero or more `MANAGER`/`MEMBER` memberships. A child account may retain `referralSourceMemberId`; all settlement attribution resolves to `commissionOwnerAccountId`, set to the organization owner. This preserves the originating sharing account while routing revenue to the enterprise owner. No enterprise UI or settlement logic is included.
