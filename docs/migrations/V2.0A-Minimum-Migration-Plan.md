# V2.0A minimum migration plan (proposal only)

No migration is executed by V2.0A. The inspected Production baseline contains event/progress tables keyed by an anonymous `session_id`, but no authenticated account or membership table. Applying a membership migration before the authoritative account schema is identified would be unsafe.

When the authenticated account schema is approved, add only these additive records:

1. `account_memberships`: one row per account; tier, status, started/expires timestamps, source, and audit timestamps.
2. `membership_resource_usage`: unique `(account_id, resource_type, resource_key)` for trial quota and unlock idempotency.
3. `indonesia_power_ledger`: unique `(account_id, resource_type, resource_key, award_type)` for server-side idempotent points.
4. `organizations` and `organization_members`: enterprise owner/member relationship and `commission_owner_account_id` attribution only.

Every table must use foreign keys to the approved account table, additive columns only, a unique index for each idempotency key, and a reversible down migration that drops only new tables/indexes. Test in non-production first; do not backfill or alter the six legacy members without a separately approved roster.
